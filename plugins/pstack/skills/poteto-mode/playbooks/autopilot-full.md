### Autopilot-full

**You own the verdicts, never the PRs. One owner carries each PR from build to merge, and nothing merges until your verifier, who never wrote the code, has proven the code that lands.**

Luca fork: Luca's layer (`~/.agents/instructions/pstack.md`, `pstack-roles/build-chat.md`) wins where it differs. The root (local build chat) runs every merge and deploy after its verdict; owners never merge (steps 2, 5). Deslop and no-comments only for large or sensitive changes (step 2). Only P0 blocks; no red test across sites (step 4). "CI" means the owner's green gate receipt on that head, not hosted CI (step 5).

A verdict covers one patch and green CI covers one head. Step 4 verifies each changed patch within its per-head limit. The patch-id rule in `playbooks/shipping.md` can carry a lane's result, and every new head needs its own green CI.

1. **The operator's gates come first.** The grant covers only the queue's items, so items the operator names as theirs and PRs outside the queue stop at merge-ready. A request to state the plan is not a go.
2. **Spawn one owner per PR, and keep its work where a replacement can find it.** Resolve the forge once for the program. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr ...` for PR create, edit, view, and watch operations; owner merges still follow Shipping step 5's expected-head rule. Otherwise stay on `gh` and record the fallback. Record the forge-reported base repository as `<base-repo>` and pass `--repo "$base_repo"` to every GitHub PR command. Resolve and validate `<head-remote>`, `<head-url>`, and `<base-remote>` separately by Shipping step 1; never assume any of them is named `origin` or that the base and head repositories are the same. Never require Graphite (`gt`). Each owner is a background subagent in its own worktree, or a Cloud task selected through [provider-dispatch](../references/provider-dispatch.md#codex-cloud-owners), that builds, opens its PR per `playbooks/opening-a-pr.md`, proves the change on the real artifact (the **prove-it-works** principle skill), babysits to green per `playbooks/babysit.md`, and merges once steps 4 and 5 clear it.

   Name every thread `PR #<number> owner|verifier|fix <scope>` or, before a PR exists, `slice:<id> owner|verifier|fix <scope>`. No unnamed role starts. Give Cloud owners only the [owner card](../references/cloud-owner-contract.md), project AGENTS.md, and slice-specific inputs; do not require this playbook, the full poteto-mode SKILL.md, or other manuals at startup. The root picks the skills each slice needs (for example ui-standard for UI or maintain-verification-skill when a flow changes) and passes them to codex-cloud-start via `--skills a,b,c`. Give verifiers the [verifier card](../references/verifier-contract.md).

   Open the PR early so CI and bots run alongside the work. The code is ready only after the slop-strip (the **deslop** skill, `/deslop`) and the `/no-comments` pass (the **no-comments** skill), so verification runs on finished code. Then rebase onto current trunk fetched through `<base-remote>` and report the code-ready head before self-proof, so verification runs on the base the patch lands on. Report every later head, and merge-ready once self-proof, CI, and babysit are done. Fix rounds stay on that base unless trunk conflicts or breaks CI, because each rebase restarts CI. Run the pre-review checks that the repo's instruction files (AGENTS.md, CLAUDE.md) name for the touched paths on the committed head before the code-ready push and before a later push that needs a verifier. A hook pass is not proof.

   Assume the owner can die. Soon after starting, push and start an uncommitted `decisions.tsv` trail per the **show-me-your-work** skill, return it with each report, then push after every unit worth keeping. Whoever spawns a subagent records its retained handle (Agent task, background Bash task, or Codex agent or session ID) and its state in a `children.tsv` kept the same way, so the root can probe it if the parent dies. Force-push only your own branch, and on any push you did not make, stop and report to the root. Before any rebase or other rewrite, apply Shipping step 4's disarm-and-confirm rule to your PR, stopping if the forge cannot confirm every request off. Fetch current trunk through `<base-remote>`. Record the selected exact commit as `<target-tip>`. Record the branch's published SHA as `<captured-sha>` with `git ls-remote -- "$head_url" "refs/heads/$branch"` and require it to equal the local pre-rebase tip. Record the branch's current patch base as `<current-base-sha>`, require `git merge-base --is-ancestor "$current_base_sha" "refs/heads/$branch"` to pass, and use `git rebase --onto "$target_tip" "$current_base_sha" -- "$branch"` when the target changed. Publish with `git push --force-with-lease="refs/heads/$branch:$captured_sha" -- "$head_url" "HEAD:refs/heads/$branch"`, pinned to the SHA you last pushed or took over.
3. **Run owners in parallel off trunk, never stacked, and keep every free item owned,** so each PR lands on its own and no item waits on you. Keep the queue as `queue.tsv` beside your `children.tsv`, one row per item with `id`, `after` (predecessor IDs), `paths` (prefixes or globs it writes), `gate` (`none` or the open operator go-gate), `state` (`todo`, `owned`, `merged`, `held`) and `owner` (retained handle), and update it on every start, merge and hold. After every owner, verifier or merge event, run `python3 <fork-checkout>/scripts/queue-free.py queue.tsv --max-active <cloud-limit>` and start an owner at once for each item it lists under "start now": predecessors merged on trunk, no path overlap with a running owner, no open go-gate. Never leave a free item for a later turn or for someone to nudge you.
4. **Verify within hard limits.** Dispatch one verifier per head by default, covering the changed flow, diff and owner receipts. A second requires a distinct coverage gap named before dispatch; more than two per PR head requires the operator's explicit go. Use the **swarm** skill's worker role within these limits. Give each verifier only the [verifier card](../references/verifier-contract.md) and its filled inputs, not manuals. The live-run entry point names the repo's `verify-<project>` skill and the feature file for the changed flow; a repo without one gets it built first with the **create-verification-skill** skill, as its own queue item every other item waits on. List every required gate in the brief with its receipt link at the candidate SHA, or mark it open or reserved for the root. Run root-reserved gates before dispatch when you can. Later rounds receive prior findings and the actual delta. Apply Shipping's patch-id rule to unchanged patches. The verdict requires an audit of merge-ready receipts and a live run of what they do not cover; repeat only missing, stale or contradicted gates, and never a failed run unchanged.

   Consolidate proven findings into one fix-forward to the PR's owner role, executed by a fresh owner agent per poteto-mode's Subagents section: original brief, all later directives, verifier findings, actual delta, branch, current head SHA and trail link. Use the same branch and owner card; name it `PR #<n> fix <scope>` and register its handle and state in `children.tsv`. Resume the prior agent only when indispensable state lives there (uncommitted work or a running process). The prior owner must have returned or be on hold before the new writer starts; never allow concurrent branch writers. Include a red test across sites sharing the defect. A trunk-only defect is recorded against trunk; a defect the PR copies or newly reaches gates the PR. Never push repairs yourself. Owners and verifiers delegate once with a full brief and block on the result; keep helper-to-helper messaging minimal, with no ping-pong.

5. **The owner merges only what you verified, tested on the trunk it lands on.** Green CI alone never authorizes a merge. The owner merges only from a head freshly rebased onto trunk. Merge prep never comes before a round's lanes start, and it ends with a rebase onto current trunk right before the merge. After the merge-prep rebase, the owner reports the new head SHA. CI must pass on that head before the merge, and the patch-id rule decides whether the round's verdict still holds. The merge-ready report records the verdict SHA and the current landing SHA. If trunk moves again before the merge, the patch ID rule in `playbooks/shipping.md` governs re-verification. A changed patch needs a new verdict. An unchanged patch keeps the verdict, but Shipping step 3 records the new `<landing-sha>` after current CI and mergeability pass. The owner lands its own PR only through Shipping step 5's server-enforced expected-head flow bound to `<landing-sha>`; never use a PR-number-only merge or unguarded auto-merge. The owner then returns. Mark the item `merged` in `queue.tsv` and run step 3's free-item check at once; each free item gets a fresh owner per poteto-mode's Subagents section. The operator's full-autonomy grant plus the root's clean verdict is the merge authorization that babysitting alone never has.
   For Cloud PRs, the local root performs only the mechanical step 5 merge and live steps permitted by project AGENTS.md; never spawn a merge owner or push repairs. Require the current head to equal the verified SHA, then use Shipping step 5's server-enforced expected head. Any new head needs verification before merge; patch-ID carryover alone does not clear this Cloud gate.
6. **Run the root layer.** On pickup, read the handoff note, not the old thread. Read large files, logs and threads only as a targeted excerpt of about 4k characters per output, or have a Luna helper summarize them. Never re-read a skill or playbook already loaded; from another playbook read only the needed section with `rg` or `sed`. Cap read output at 2000 tokens (`max_output_tokens`); only build and test logs may exceed it, and then only their tail. One exec's whole output enters context, so never bundle several large reads into one exec; give them to a Luna explorer that returns only a summary. The 2000-token cap applies per call, not per file. Always read the spec, acceptance criteria, owner and verifier final states and the handoff note verbatim, in several 2000-token sections if needed, and never let Luna summarize them, because a summary can drop the detail a gate or acceptance hangs on. Anything that loosens a gate, such as a raised budget or an allowlist entry, needs a verifier's proof and then your fresh countersign, because the owner is the one who wants green. Under a grant that covers approvals, that countersign is the approval, and the owner's record of it points at your countersign for a lane to check. A disabled or soft-failed check always comes out, because it stops guarding every case. Never give or bypass an approval the forge enforces, because no countersign covers it.

   On the operator's go, arm `/loop 1h` to audit until no delegated work is left, because long runs drift and agents stall silently. The tick is an observation cadence, never a lease, deadline, or cancellation threshold. Each tick runs `python3 <fork-checkout>/scripts/thread-tokens.py <state.sqlite> --since <run-start-ms> --until <now-ms> --repo <git-origin-url-or-cwd> --root-thread <build-chat-id> --check`, adding one `--cloud-owner` argument per Cloud start receipt as defined in [provider-dispatch](../references/provider-dispatch.md#codex-cloud-owners); treat violations as drift to fix through the owner role, never by weakening limits. Each tick also runs `python3 <fork-checkout>/scripts/queue-free.py queue.tsv --max-active <cloud-limit> --check`; a free item without an owner is drift, fixed in the same tick by starting its owner. Each tick re-reads this playbook from disk (`skills/poteto-mode/playbooks/autopilot-full.md` under the installed plugin) and fixes drift, such as an unreported head, an unrecorded agent, or an owner that has neither pushed nor written a trail row, by having its owner record it, because drift is a gap in the record, not a stall. It probes every agent through its retained handle, down to the leaf lanes in each `children.tsv`, and judges each by its side effects, because status text and summaries can hide a stuck child. An agent is stuck only on affirmative failure evidence: it errors, its process is dead, its handle fails, it cannot start turns, or a caller-supplied external deadline passed. Elapsed time or the absence of a new side effect alone never proves it stuck; implementation runs can stay healthy for 90 minutes or much longer. One waiting on you or the operator is not stuck, so answer it. Cancel a stuck agent through its retained handle and replace it at once, without waiting for its stop to land. A tick that changed something for the operator ends by catching them up per the **ketchup** skill, and one that changed nothing stays quiet.
7. **Stand down at once on the operator's stop.** A hold reaches every owner as a zero-writes order. Each reports where it stands and keeps its brief until the operator releases it.

**Reply:** catch the operator up per the **ketchup** skill, covering each PR's state and verdict, what merged, countersigns and why, and open operator gates, with links to each PR and the trails.
