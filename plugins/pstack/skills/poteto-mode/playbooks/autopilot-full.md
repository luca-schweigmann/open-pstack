### Autopilot-full

**You own the verdicts, never the PRs. One owner carries each PR from build to merge, and nothing merges until your swarm, which never wrote the code, has proven the code that lands.**

A verdict covers one patch and green CI covers one head. Step 4 runs a full swarm once, and again only for a major change. The patch-id rule in `playbooks/shipping.md` can carry a lane's result, and every new head needs its own green CI.

1. **The operator's gates come first.** The grant covers only the queue's items, so items the operator names as theirs and PRs outside the queue stop at merge-ready. A request to state the plan is not a go.
2. **Arm the step 6 audit loop, then spawn one owner per PR, and keep its work where a replacement can find it.** Resolve the forge once for the program. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr ...` for PR create, edit, view, and watch operations; owner merges still follow Shipping step 5's expected-head rule. Otherwise stay on `gh` and record the fallback. Record the forge-reported base repository as `<base-repo>` and pass `--repo "$base_repo"` to every GitHub PR command. Resolve and validate `<head-remote>`, `<head-url>`, and `<base-remote>` separately by Shipping step 1; never assume any of them is named `origin` or that the base and head repositories are the same. Never require Graphite (`gt`). Each owner is a background subagent in its own worktree, or a Codex Cloud task when the sheet selects that route, that builds, opens its PR per `playbooks/opening-a-pr.md`, proves the change on the real artifact (the **prove-it-works** principle skill), babysits to green per `playbooks/babysit.md`, and merges once steps 4 and 5 clear it.

   Open the PR early so CI and bots run alongside the work. The code is ready only after the slop-strip (the **deslop** skill, `/deslop`) and the `/no-comments` pass (the **no-comments** skill), so the full swarm runs on finished code. Then rebase onto current trunk fetched through `<base-remote>` and report the code-ready head before self-proof, so verification runs on the base the patch lands on. Report every later head, and merge-ready once self-proof, CI, and babysit are done. Fix rounds stay on that base unless trunk conflicts or breaks CI, because each rebase restarts CI. Run the pre-review checks that the repo's instruction files (AGENTS.md, CLAUDE.md) name for the touched paths on the committed head before the code-ready push and before a later push that needs a verifier. A hook pass is not proof.

   Assume the owner can die. Soon after starting, push and start an uncommitted `decisions.tsv` trail per the **show-me-your-work** skill, return it with each report, then push after every unit worth keeping. Whoever spawns a subagent records its retained handle (Agent task, background Bash task, or Codex agent or session ID) and its state in a `children.tsv` kept the same way, so the root can probe it if the parent dies. Force-push only your own branch, and on any push you did not make, stop and report to the root. Before any rebase or other rewrite, apply Shipping step 4's disarm-and-confirm rule to your PR, stopping if the forge cannot confirm every request off. Fetch current trunk through `<base-remote>`. Record the selected exact commit as `<target-tip>`. Record the branch's published SHA as `<captured-sha>` with `git ls-remote -- "$head_url" "refs/heads/$branch"` and require it to equal the local pre-rebase tip. Record the branch's current patch base as `<current-base-sha>`, require `git merge-base --is-ancestor "$current_base_sha" "refs/heads/$branch"` to pass, and use `git rebase --onto "$target_tip" "$current_base_sha" -- "$branch"` when the target changed. Publish with `git push --force-with-lease="refs/heads/$branch:$captured_sha" -- "$head_url" "HEAD:refs/heads/$branch"`, pinned to the SHA you last pushed or took over.
   **Cloud owner brief additions.** The build root is a local Codex Sol session created through session_bridge `codex_create_visible_session`, visible and pinned through `codex_move_thread_to_sidebar_section` with `sectionId: "pinned"`; read back both states before handing it the queue. Do not use `codex_create_thread`. Manage queued items and terminal slot release through the Cloud route rules. Resolve `pr owners` through [provider-dispatch](../references/provider-dispatch.md#codex-cloud-owners), falling back to the sheet's `feature, refactoring` line only when that role is absent. Pass the owner the slice, exact starting SHA, repository gate list from AGENTS.md, branch and forge identities, fork and project checkout paths, and the owner duties above. For every subagent the Cloud owner starts through `collaboration.spawn_agent`, the brief must fix the absolute project-checkout path and require its first actions to be `cd <absolute-project-checkout>` and `git rev-parse --show-toplevel`. If either command fails or the reported top-level path is not the assigned checkout, the subagent must stop before further work and report the failure to its owner. Cloud subagents have been observed starting in `/workspace` outside the repository, where Git exits 128; never rely on an inherited working directory. The first action is `node <fork-checkout>/scripts/cloud-owner-preflight.mjs <fork-checkout> <project-checkout>`. Paste its evidence into the task, then read the installed poteto-mode SKILL.md, this playbook's owner duties, [cloud-owner-contract](../references/cloud-owner-contract.md), and the project AGENTS.md. If preflight fails, report `blocked` and stop without building; never continue without the skills. Apply poteto-mode, its principles, deslop, no-comments, technical-writing, and the decisions trail. In Cloud, use the GitHub connector to open and update the PR and read its checks; `gh` and Origin commands in the local playbooks do not apply there. Push only the assigned branch. Receive no live credentials or real customer data, and perform no live steps. End every turn with this JSON block, using actual command exit codes and a durable trail link. A blocked report may use null for a PR not yet created or a head not yet available; a code-ready report requires both and all required gates green.

   ```json
   {
     "state": "code-ready",
     "prUrl": "<PR URL>",
     "headSha": "<full head SHA>",
     "gates": [{"command": "<gate command>", "exitCode": 0}],
     "trailUrl": "<decisions trail link>"
   }
   ```

   Use `code-ready`, `blocked`, or `failed` as the state. If preflight fails before a trail exists, `trailUrl` may be null and `gates` empty. Report the blocker or failure reason immediately before the block. `code-ready` hands the head to the root for verification; it is never merge authorization. After each fix-forward, repeat the gates required for the new head and return an updated block. The local root waits through `--read --wait`, runs the configured Luna verify swarm locally on the reported PR head, and sends the collected findings with `--send --prompt-file` to the same Cloud owner on the same PR.

   **Cloud route deviation from vanilla owner-merges.** For a Cloud owner, the local build root performs step 5's verified expected-head merge through local `gh` after its pstack verdict, and all live steps, under the repo AGENTS.md release rule. The owner still owns repairs and green gates; the root never pushes a fix. Tier 1 permits merge and deploy with rollback after green. Tier 2 permits migrations and data steps only with a recorded restore point, a dry run on a copy, no deletion, and a fresh independent reviewer's OK. Tier 3 leaves real customer data sent to a new recipient, permanent deletes, new access, keys, and logins to Luca. Changes touching real customer data also need an Opus or Oracle security review before merge; that review runs locally.

3. **Run owners in parallel off trunk, never stacked,** so each PR lands on its own.
4. **Swarm-verify once.** A full swarm runs once, at the code-ready head. Another full swarm runs only for new behavior, a redesign, or a large new diff. A rebase, a merge-conflict resolution, or a minor fix gets a single verifier at the new head. Fan out independent verifiers at the code-ready SHA per the **swarm** skill. They re-run the gates, prove the load-bearing behavior live on the real surface through its driver skill (`run` for CLIs and TUIs, `verify` for UIs) or a named driver, and audit the diff. The verdict is not clean without the live lane, or before you audit the merge-ready report's receipts, because no lane trusts a claim it has not checked.

   Send every proven finding, whatever a lane labeled it, to the owner in one fix-forward, with a red test across every site with the same defect. A defect trunk shows without the PR is recorded against trunk and does not gate the PR, but one the PR copies or newly reaches is the PR's own. Never push a fix yourself, because each branch has one writer. Replace a stuck owner instead.
5. **The owner merges only what you verified, tested on the trunk it lands on.** Green CI alone never authorizes a merge. The owner merges only from a head freshly rebased onto trunk. Merge prep never comes before a round's lanes start, and it ends with a rebase onto current trunk right before the merge. After the merge-prep rebase, the owner reports the new head SHA. CI must pass on that head before the merge, and the patch-id rule decides whether the round's verdict still holds. The merge-ready report records the verdict SHA and the current landing SHA. If trunk moves again before the merge, the patch ID rule in `playbooks/shipping.md` governs re-verification. A changed patch needs a new verdict. An unchanged patch keeps the verdict, but Shipping step 3 records the new `<landing-sha>` after current CI and mergeability pass. The owner lands its own PR only through Shipping step 5's server-enforced expected-head flow bound to `<landing-sha>`; never use a PR-number-only merge or unguarded auto-merge. The owner then returns. A fresh owner picks up the next self-contained item from the queue, per poteto-mode's Subagents section. The operator's full-autonomy grant plus the root's clean verdict is the merge authorization that babysitting alone never has.
6. **Run the root layer.** Anything that loosens a gate, such as a raised budget or an allowlist entry, needs a verifier's proof and then your fresh countersign, because the owner is the one who wants green. Under a grant that covers approvals, that countersign is the approval, and the owner's record of it points at your countersign for a lane to check. A disabled or soft-failed check always comes out, because it stops guarding every case. Never give or bypass an approval the forge enforces, because no countersign covers it.

   Arm `/loop 1h` before the first owner spawns, because the autopilot-full invocation is the operator's go, and audit until no delegated work is left, because long runs drift and agents stall silently. The tick is an observation cadence, never a lease, deadline, or cancellation threshold. Each tick re-reads this playbook from disk (`skills/poteto-mode/playbooks/autopilot-full.md` under the installed plugin) and fixes drift, such as an unreported head, an unrecorded agent, or an owner that has neither pushed nor written a trail row, by having its owner record it, because drift is a gap in the record, not a stall. It probes every agent through its retained handle, down to the leaf lanes in each `children.tsv`, and judges each by its side effects, because status text and summaries can hide a stuck child. An agent is stuck only on affirmative failure evidence: it errors, its process is dead, its handle fails, it cannot start turns, or a caller-supplied external deadline passed. Elapsed time or the absence of a new side effect alone never proves it stuck; implementation runs can stay healthy for 90 minutes or much longer. One waiting on you or the operator is not stuck, so answer it. Cancel a stuck agent through its retained handle and replace it at once, without waiting for its stop to land. A tick that changed something for the operator ends by catching them up per the **ketchup** skill, and one that changed nothing stays quiet.
7. **Stand down at once on the operator's stop.** A hold reaches every owner as a zero-writes order. Each reports where it stands and keeps its brief until the operator releases it.

**Reply:** catch the operator up per the **ketchup** skill, covering each PR's state and verdict, what merged, countersigns and why, and open operator gates, with links to each PR and the trails.
